## 2. Por qué

- **Instalar .NET 10 con pacman (previa autorización):** el briefing exige .NET 10 y el SDK 8 no compila `net10.0`. El SDK 10 convive con el 8 (instalaciones lado a lado). Las reglas pedían permiso antes de cualquier `sudo`.
- **Runtime y targeting packs aparte:** el SDK compila, pero ejecutar necesita el runtime; sin él, el `hello-world` falló. Lo verificamos con un programa real y no nos fiamos del `--list-sdks`.
- **`uv` + Python 3.12:** Python solo se usa **una vez** para exportar `yolo11n.pt` → `.onnx`. El Python 3.14 del sistema es demasiado nuevo para tener wheels fiables de `ultralytics`/`onnx`. `uv` descarga y aísla un 3.12 sin tocar el sistema.
- **No usar Python en la app:** el runtime de la demo es 100 % .NET + ONNX; así el lunes no depende de Python ni de internet. El `.onnx` irá versionado en el repo.
- **Demo en el PC Linux, no en el portátil:** el portátil ya está cargado con Meet y su webcam (la de la cara) solo tiene un dueño. Cada dispositivo hace una cosa: portátil = videollamada, PC = inferencia, iPhone = cámara de objetos.
- **Compartir la pestaña de Chrome:** Meet da mejor calidad de vídeo al compartir pestaña que ventana o pantalla.
- **Spike propio en lugar de DroidCam:** menos latencia, sin marca de agua, y nos da el patrón que reutilizamos (`IFrameSource`). Python para el spike es válido porque es un experimento desechable; el código final será C#.
- **Plan B (vídeo grabado):** si la cámara o el wifi fallan, la misma app lee un MP4 en bucle cambiando `Camera:Source`.

## 3. Conceptos usados

### 3.1 SDK vs runtime vs ASP.NET Core runtime
| Pieza | Para qué sirve | Ejemplo aquí |
|---|---|---|
| **SDK** | Compilar, `dotnet build/test/new`, incluye herramientas | `dotnet-sdk 10.0.114` |
| **Runtime (`Microsoft.NETCore.App`)** | Ejecutar apps de consola/librerías (CLR, BCL) | `dotnet-runtime 10.0.14`; faltaba y nada arrancaba |
| **ASP.NET Core runtime (`Microsoft.AspNetCore.App`)** | Kestrel, MVC, Blazor, SignalR | `aspnet-runtime 10.0.14`; lo necesita QualityVision.Web |
| **Targeting packs** | Ensamblados de referencia con los que se compila contra `net10.0` | Instalados aparte |

Idea clave: **compilar ≠ ejecutar**. En un servidor de producción solo se instala el runtime, no el SDK. Comprobación:

```bash
dotnet --list-sdks        # SDKs instalados (8.0.133 y 10.0.114)
dotnet --list-runtimes    # runtimes (debe salir Microsoft.NETCore.App 10.0.14)
```

### 3.2 `global.json` y fijado del SDK
Con varios SDKs, `dotnet` usa por defecto el más alto. `global.json` en la raíz **fija** cuál usar, así cualquiera (o CI) compila igual:

```json
{ "sdk": { "version": "10.0.114", "rollForward": "latestFeature" } }
```

`rollForward` permite parches/features posteriores sin romper. Esto evita el clásico "en mi máquina funciona". (Revisa el valor real en el `global.json` del repo.)

### 3.3 Python solo para exportar (ultralytics → ONNX) y `uv`
`ultralytics` (PyTorch) es el framework en el que se entrenó YOLO11. Necesitamos **convertir** el modelo una vez; en ejecución solo hace falta ONNX Runtime desde C#. `uv` crea entornos reproducibles y gestiona versiones de Python:

```bash
uv run --python 3.12 --with ultralytics python export.py   # no usa el 3.14 del sistema
```

Ejemplo del proyecto: el 3.14 del sistema queda intacto; el 3.12 vive aislado en el entorno de `uv`.

### 3.4 ONNX, opset 17 y entrada estática
- **ONNX**: formato abierto de modelos, independiente del framework. Permite entrenar en Python y ejecutar en C# (ONNX Runtime).
- **Opset 17**: versión del conjunto de operadores; el runtime que usa YoloDotNet debe soportarla. Fijarla evita errores de "operador no soportado".
- **Entrada estática** (`dynamic=False`, `1x3x640x640`): batch, canales y tamaño fijos. Más rápido, más predecible y compatible con YoloDotNet. Contrapartida: cada frame se redimensiona a 640x640 (letterbox).

```python
YOLO("yolo11n.pt").export(format="onnx", opset=17, dynamic=False, imgsz=640)
```

### 3.5 MJPEG (`multipart/x-mixed-replace`)
MJPEG = secuencia de JPEGs independientes. Sobre HTTP se manda **una sola respuesta que nunca termina**, con partes separadas por un *boundary*:

```
Content-Type: multipart/x-mixed-replace; boundary=frame

--frame
Content-Type: image/jpeg
Content-Length: 41234

<bytes JPEG>
--frame
...
```

El navegador **sustituye** (mixed-replace) la imagen en cada parte. Por eso `<img src="/stream">` funciona sin JavaScript. Ventajas: trivial, sin códecs de vídeo, baja latencia, cualquier navegador. Desventaja: más ancho de banda que H.264. Perfecto para una demo en LAN. DroidCam sirve MJPEG, y nuestro endpoint `/stream` (M2) también.

### 3.6 HTTPS, contexto seguro y certificados autofirmados
`navigator.mediaDevices.getUserMedia` (acceso a la cámara) solo existe en un **contexto seguro**: HTTPS o `localhost`. El iPhone accede por IP de LAN (`http://192.168.18.62`), que **no** es segura → Safari bloquea la cámara. Solución: servir HTTPS con un certificado **autofirmado** generado con `openssl` e incluyendo la IP en el `subjectAltName`:

```bash
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=192.168.18.62" -addext "subjectAltName=IP:192.168.18.62,IP:127.0.0.1"
```

Cifra igual que uno "real", pero ninguna CA lo avala, así que Safari avisa y hay que aceptar la excepción una vez. Las claves están en `certs/`, **fuera de git**. En producción se usaría una CA real (Let's Encrypt o PKI interna).

### 3.7 Backpressure (una petición en vuelo)
El móvil no envía el frame N+1 hasta recibir respuesta del N. Si la red va lenta, se **descartan** frames en el origen en lugar de acumularlos en colas. Mismo principio que `Channel` acotado con `DropOldest` en el pipeline (M2): mejor perder un frame viejo que ver imagen con segundos de retraso.

## 4. 3 preguntas que te pueden hacer

**1. ¿Por qué no usar la webcam del portátil?**
Porque en la entrevista por Meet esa webcam ya se usa para mi cara y una cámara solo tiene un dueño; además apuntaría hacia mí, no a los objetos. Separé funciones: el portátil lleva Meet, el PC Linux ejecuta la inferencia (12 hilos, no compite con Meet) y un iPhone en trípode enfoca los objetos. El PC además no tiene webcam, así que de todas formas necesitaba una cámara de red.

**2. ¿Por qué la latencia era mayor con DroidCam en MPV que con tu página?**
Los FPS eran buenos (~30 FPS medidos con `ffmpeg`), así que no era la red. El retraso lo añadía el **buffer del reproductor** (MPV acumula frames para suavizar). Mi spike mide la edad del frame al recibirlo (~40 ms de media, picos de ~119 ms), solo mantiene **una petición en vuelo** (backpressure: si algo va lento, se pierden frames, no se acumulan) y la app consume el último frame directamente, sin buffer de reproductor. Matiz honesto: son medidas de contextos distintos; lo importante es que el diseño elimina las colas.

**3. ¿Cómo garantizas que la demo funciona si falla la cámara?**
Con un **Plan B**: la fuente de frames es una abstracción (`IFrameSource`) con implementaciones para móvil/webcam y para archivo de vídeo en bucle (`samples/demo.mp4`). Cambiar de una a otra es una línea de configuración (`Camera:Source`), y está previsto que si se pierde la cámara la app reintente con backoff y vuelva sola al vídeo, con un indicador en el dashboard. Además hay un Plan C: compartir un MP4 grabado de la demo completa y enseñar el código. Y el ensayo del domingo de 10 minutos, con arranque desde cero, valida todo ello.
