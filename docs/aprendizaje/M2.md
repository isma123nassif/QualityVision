# M2 — Captura, canal y streaming MJPEG

> Primer milestone con lógica real: una imagen entra por el iPhone (o URL, webcam, vídeo), cruza un canal acotado, se dibuja la Prüfzone y sale como vídeo MJPEG al navegador. Todavía **no hay detección** (YOLO llega en M3). Su valor en la entrevista: muestra cómo manejas memoria, concurrencia y apagado limpio en un pipeline en tiempo real.

---

## Qué se hizo

- **Core (sin paquetes):** `Frame` (imagen BGRA en un buffer del pool), `IFrameSource`, `FrameSourceException` y `NormalizedRect` (la Prüfzone en coordenadas 0..1).
- **Infrastructure:** `PhoneFrameSource` (recibe JPEG del móvil), `OpenCvFrameSource` (URL, webcam V4L2, vídeo en bucle), `FrameSourceFactory`, `JpegFrameEncoder` (dibuja la zona y codifica JPEG), `MatFrameConverter`, `PinnedMat` y `JpegHeader`.
- **Web:** `CameraService` (productor), `DetectionService` (consumidor), `FrameBroadcaster`, `CameraStatus`, `FrameUploadGate` y `CameraEndpoints` (`GET /stream`, `POST /api/camera/frame`, `GET /api/camera/status`, `GET /kamera`).
- **Front:** `wwwroot/kamera.html` (página de captura del iPhone) y el dashboard `Home.razor` con el stream y el estado de la cámara.
- **Kestrel** con dos endpoints: HTTP `:5080` (dashboard y `/stream`) y HTTPS `:5443` (solo página del móvil y subida de frames).
- **Tests:** 69 tras QA y **94** tras corregir la revisión.

Flujo de datos de M2:

```mermaid
flowchart LR
    A["iPhone: kamera.html"] -->|"POST /api/camera/frame (HTTPS)"| B["PhoneFrameSource"]
    B -->|"canal interno, capacidad 1"| C["CameraService"]
    C -->|"Channel&lt;Frame&gt; (2, DropOldest)"| D["DetectionService"]
    D --> E["JpegFrameEncoder"]
    E --> F["FrameBroadcaster"]
    F -->|"GET /stream (multipart/x-mixed-replace)"| G["Navegador: dashboard"]
```

Las otras fuentes (`OpenCvFrameSource`: URL, webcam, vídeo) entran en el mismo punto que `PhoneFrameSource`: las dos implementan `IFrameSource`, así que `CameraService` no sabe de dónde vienen los frames.

Lo que **todavía no existe**: detección, reglas, persistencia, cambio de fuente en caliente (hay que reiniciar para cambiar `Camera:Source`; está documentado en `CameraService.cs:1-13` como M6).

---

## Por qué

- **`Frame` con buffer del pool y `Dispose`:** a 15–20 FPS, 1280×720×4 bytes son ~3,7 MB por frame. Si cada uno fuera un `new byte[]`, el GC del LOH (Large Object Heap) trabajaría sin parar. El pool reutiliza los arrays.
- **Canal acotado con `DropOldest`:** si la inferencia (M3) es más lenta que la cámara, no queremos una cola infinita (memoria y latencia crecientes). Preferimos tirar el frame viejo: en inspección en vivo, el frame más nuevo es el único útil.
- **Dos canales:** uno de capacidad 1 dentro de `PhoneFrameSource` (los POST HTTP llegan en paralelo) y otro de capacidad 2 entre `CameraService` y `DetectionService`.
- **`FrameBroadcaster` codifica una vez para N clientes:** se codifica el JPEG una sola vez y todos los `/stream` comparten el mismo `byte[]` inmutable. Un cliente lento solo se salta frames; nunca frena a `Publish`.
- **MJPEG en lugar de WebRTC:** `<img src="/stream">` funciona en cualquier navegador, sin JavaScript ni señalización ICE/STUN. Cuesta más ancho de banda, pero en una LAN da igual. (Ver pregunta 3.)
- **HTTPS solo para el móvil:** `getUserMedia` (acceso a la cámara) exige un *secure context*: HTTPS o `localhost`. El iPhone no es `localhost`, así que necesita HTTPS con certificado autofirmado. El dashboard y el stream siguen en HTTP para evitar avisos de certificado en la demo.
- **Reintento con backoff exponencial:** una cámara por red se cae. `CameraService` reintenta a 1, 2, 4… máx. 10 s y no tumba nunca el host.
- **`TimeProvider`:** el reloj es inyectable; los tests controlan el tiempo con un `FakeTimeProvider` en vez de esperar de verdad.
- **Opciones validadas al arrancar:** una configuración rota debe fallar en el arranque, no a mitad de la demo.
- **Contrato primero:** `docs/contracts/M2-contract.md` fijó las firmas antes de escribir código, para que tres agentes trabajaran en paralelo sin pisarse (sección 4).

## Conceptos de C# / .NET

### `IDisposable` + `ArrayPool` + `Interlocked` (`Frame`)

Un `Frame` posee un buffer alquilado a `ArrayPool<byte>.Shared`. Quien lo recibe debe hacer `Dispose` para devolverlo. Pero puede haber dos llamadas a la vez (por ejemplo el canal descarta el frame y a la vez el consumidor termina). `Interlocked.Exchange` es atómico: solo un hilo ve el buffer; el otro ve `null`. Resultado: se devuelve **exactamente una vez**.

```csharp
// src/QualityVision.Core/Frames/Frame.cs:78-86
public void Dispose()
{
    // Interlocked.Exchange guarantees that only one caller ever sees the buffer, so it is returned once.
    byte[]? buffer = Interlocked.Exchange(ref _buffer, null);
    if (buffer is not null)
    {
        _returnBuffer?.Invoke(buffer);
    }
}
```

Tras el `Dispose`, `UnsafeBuffer` lanza `ObjectDisposedException` (`Frame.cs:68-76`): usar un frame ya devuelto sería leer memoria que otro ya está reutilizando. `Core` no conoce `ArrayPool`; recibe un `Action<byte[]>`, así se testea sin pool y `Core` sigue sin paquetes.

### `IAsyncEnumerable<T>`, `await foreach` y `yield return`

Una fuente de frames es un flujo asíncrono sin fin. `IAsyncEnumerable<Frame>` permite consumirlo con `await foreach`. `[EnumeratorCancellation]` conecta el token que pasa el consumidor con el del método iterador.

```csharp
// src/QualityVision.Infrastructure/Camera/PhoneFrameSource.cs:121-128
public async IAsyncEnumerable<Frame> ReadFramesAsync([EnumeratorCancellation] CancellationToken cancellationToken)
{
    await foreach (Frame frame in _latest.Reader.ReadAllAsync(cancellationToken).ConfigureAwait(false))
    {
        // Ownership of the frame transfers to the consumer.
        yield return frame;
    }
}
```

Regla de propiedad: **el consumidor posee y libera cada frame**. La revisión comprobó que no hay ningún `await` entre `yield return` y `TryWrite`, así que una cancelación no puede perder la propiedad de un frame.

### `Channel<T>` acotado, `DropOldest` e `itemDropped`

`Channel<T>` es una cola asíncrona productor/consumidor. Con `BoundedChannelFullMode.DropOldest`, si está llena, expulsa el elemento más viejo. Ese elemento es un `Frame` con buffer del pool: sin avisarnos se perdería sin `Dispose`. Por eso existe el callback `itemDropped`.

```csharp
// src/QualityVision.Web/Program.cs:37-44
builder.Services.AddSingleton<Channel<Frame>>(_ => Channel.CreateBounded<Frame>(
    new BoundedChannelOptions(2)
    {
        FullMode = BoundedChannelFullMode.DropOldest,
        SingleReader = true,
        SingleWriter = true,
    },
    static dropped => dropped.Dispose()));
```

`SingleReader`/`SingleWriter` permiten una implementación más rápida, pero solo son válidos si es cierto: aquí hay un solo `CameraService` y un solo `DetectionService`. En `PhoneFrameSource` (`:42-49`) son `false` porque varios POST pueden escribir a la vez.

### `BackgroundService`, backoff exponencial y `TimeProvider`

`BackgroundService` es la base de los servicios de larga duración del host. `ExecuteAsync` recibe un `stoppingToken` que se cancela al apagar. El filtro `when` deja pasar la cancelación de apagado, pero captura cualquier otro fallo de la cámara y lo convierte en un reintento.

```csharp
// src/QualityVision.Web/Pipeline/CameraService.cs:65-82
catch (Exception ex) when (ex is not OperationCanceledException || !stoppingToken.IsCancellationRequested)
{
    logger.LogError(ex, "Frame source {Source} failed", sourceName);
    // German text for the UI; the raw exception stays in the log.
    status.ReportDisconnected(FormattableString.Invariant($"Kamera nicht erreichbar – neuer Versuch in {SecondsOf(backoff)} s"));
}
...
await Task.Delay(backoff, timeProvider, stoppingToken);
backoff = TimeSpan.FromTicks(Math.Min(backoff.Ticks * 2, MaxBackoff.Ticks));
```

`Task.Delay(…, timeProvider, …)` usa el reloj inyectado: con `FakeTimeProvider` el test avanza el tiempo a mano. El backoff vuelve a 1 s en cuanto llega un frame (`CameraService.cs:44-48`). El `finally` siempre libera la fuente.

### `TaskCompletionSource` con `RunContinuationsAsynchronously` (`FrameBroadcaster`)

Cada cliente de `/stream` espera "el siguiente frame". `FrameBroadcaster` guarda un `TaskCompletionSource` compartido; `Publish` lo completa y crea uno nuevo para la siguiente ronda. **Todos** los clientes esperan la misma tarea.

```csharp
// src/QualityVision.Web/Pipeline/FrameBroadcaster.cs:32-41
lock (_gate)
{
    published = (jpeg, (_latest?.Sequence ?? 0) + 1);
    _latest = published;
    waiters = _next;
    _next = NewWaiter();
}

// Completed outside the lock; continuations run asynchronously, so Publish never runs client code.
waiters.TrySetResult(published);
```

```csharp
// src/QualityVision.Web/Pipeline/FrameBroadcaster.cs:64-65
private static TaskCompletionSource<(byte[] Jpeg, long Sequence)> NewWaiter() =>
    new(TaskCreationOptions.RunContinuationsAsynchronously);
```

Sin `RunContinuationsAsynchronously`, `TrySetResult` podría ejecutar el código de los clientes **en el hilo de `Publish`**, y un cliente lento bloquearía el pipeline. Con la opción, las continuaciones van al ThreadPool. Además se completa fuera del `lock` para no ejecutar nada ajeno con el cerrojo tomado. Los clientes usan `next.WaitAsync(ct)` (`:61`): cancelar a uno no completa ni rompe la tarea de los demás.

### `CancellationTokenSource.CreateLinkedTokenSource` (el stream termina al apagar)

Un `/stream` abierto esperaba solo `RequestAborted` (el cliente se desconecta). Al hacer Ctrl+C, `DetectionService` para, `Publish` ya no se llama y la espera no termina nunca; Kestrel espera a las peticiones en curso hasta `ShutdownTimeout` (30 s). El dashboard siempre tiene un stream abierto, así que **cada parada tardaba ~30 s**. Fue el MAJOR #1 de la revisión. La solución: un token enlazado que se cancela con cualquiera de los dos.

```csharp
// src/QualityVision.Web/Endpoints/CameraEndpoints.cs:51-54
// Also end on host shutdown, otherwise open streams would delay application stop.
using CancellationTokenSource linked = CancellationTokenSource.CreateLinkedTokenSource(
    context.RequestAborted, lifetime.ApplicationStopping);
CancellationToken ct = linked.Token;
```

Medido tras el arreglo: **51 ms frente a ~30 s**. El `using` libera el CTS enlazado al terminar la petición (si no, queda registrado en `ApplicationStopping`).

### Minimal APIs y `multipart/x-mixed-replace`

Las minimal APIs mapean rutas a funciones con `MapGet`/`MapPost`; los parámetros (`HttpContext`, servicios, `CancellationToken`) se inyectan solos. MJPEG es una respuesta HTTP que **nunca termina**: cada parte lleva su cabecera y un JPEG, y el navegador reemplaza la imagen anterior.

```csharp
// src/QualityVision.Web/Endpoints/CameraEndpoints.cs:56-58, 68-75
response.ContentType = "multipart/x-mixed-replace; boundary=frame";
response.Headers.CacheControl = "no-store";
context.Features.Get<IHttpResponseBodyFeature>()?.DisableBuffering();
...
byte[] partHeader = Encoding.ASCII.GetBytes(string.Create(
    CultureInfo.InvariantCulture,
    $"--frame\r\nContent-Type: {JpegContentType}\r\nContent-Length: {jpeg.Length}\r\n\r\n"));

await response.Body.WriteAsync(partHeader, ct);
await response.Body.WriteAsync(jpeg, ct);
```

`DisableBuffering` es clave: sin él, Kestrel acumularía bytes y el vídeo llegaría a trompicones. `CultureInfo.InvariantCulture` evita que un `Content-Length` salga con separador de miles en otra cultura.

### `IOptionsMonitor<T>` + `ValidateOnStart`

`IOptionsMonitor<T>` lee la configuración actual y se entera de los cambios en `appsettings.json`. `ValidateOnStart` ejecuta las validaciones **al arrancar el host**, no la primera vez que alguien pide la opción.

```csharp
// src/QualityVision.Infrastructure/DependencyInjection.cs:19-24, 31-33
services.AddOptions<CameraOptions>()
    .Bind(configuration.GetSection(CameraOptions.SectionName))
    .Validate(static o => Enum.IsDefined(o.Source),
        "Camera:Source must be one of Phone, Url, Webcam, VideoFile.")
    .Validate(static o => o.Source != CameraSourceKind.Url || IsStreamUrl(o.Url),
        "Camera:Url must be an absolute http, https or rtsp URL when Camera:Source is Url.")
...
    .ValidateOnStart();
```

Así un `Camera:Source = "Url"` sin URL válida rompe el arranque con un mensaje claro. Consumidores como `DetectionService` leen `CurrentValue` en cada frame, de modo que un cambio de calidad JPEG se aplica sin reiniciar. Según la revisión, `InspectionOptions.Zone` (un `record struct`) se enlaza bien con el binder por reflexión, y un test (`OptionsBindingTests`) lo comprueba con valores **distintos** de los de por defecto.

### Kestrel: endpoints HTTP/HTTPS y por qué HTTPS

```json
// src/QualityVision.Web/appsettings.json:9-15
"Kestrel": {

      "Url": "http://0.0.0.0:5080"
    }

```

El endpoint HTTPS `:5443` va en `appsettings.Local.json`, **ignorado por git**, con rutas a un certificado fuera del repo (`Program.cs:11-17`). El certificado es autofirmado: el iPhone muestra un aviso que hay que aceptar una vez. Las rutas del móvil se atan al puerto con `RequireHost("*:5443")` **y** una comprobación `IsHttps`:

```csharp
// src/QualityVision.Web/Endpoints/CameraEndpoints.cs:33-37
// RequireHost matches the port only; IsHttps additionally guarantees a secure context (404 otherwise).
endpoints.MapGet("/kamera", (HttpContext context) => context.Request.IsHttps
```

Esto salió de la revisión (MINOR #7): `RequireHost` compara la cabecera `Host`, que el cliente puede falsificar, no el puerto real de escucha.

### `SemaphoreSlim` como puerta de subida

El móvil se auto-limita, pero un cliente malicioso no. `FrameUploadGate` permite como máximo 2 subidas a la vez, y **nunca espera**: `Wait(0)` devuelve `false` al instante y el endpoint contesta 503.

```csharp
// src/QualityVision.Web/Pipeline/FrameUploadGate.cs:9-16
private const int MaxConcurrentUploads = 2;

private readonly SemaphoreSlim _semaphore = new(MaxConcurrentUploads, MaxConcurrentUploads);

/// <summary>Tries to take a slot without waiting. A <c>true</c> result must be paired with <see cref="Release"/>.</summary>
public bool TryEnter() => _semaphore.Wait(0);

public void Release() => _semaphore.Release();
```

En `PostFrameAsync` (`CameraEndpoints.cs:131-161`) el `Release` está en el `finally`, emparejado con el `Return` del buffer del pool. Esperar en cola solo acumularía trabajo: es mejor rechazar rápido.

### Comprobar la cabecera SOF del JPEG (bombas de descompresión)

Limitar el tamaño en bytes (2 MB) no limita los **píxeles**: un JPEG pequeño puede declarar hasta 2^30 px, y `ImDecode` reservaría ~3 GB antes de reducir la imagen. Era el MAJOR #3. La defensa es leer el tamaño declarado en la cabecera SOFn **sin decodificar** y rechazar lo que supere 4096 px por lado.

```csharp
// src/QualityVision.Infrastructure/Camera/PhoneFrameSource.cs:77-86
// Decompression-bomb guard: a < 2 MB JPEG can declare up to 2^30 px, and ImDecode would allocate the full
// bitmap (~3 GB) before any downscale. Check the declared size in the SOFn header first.
if (!JpegHeader.TryReadSize(jpeg, out int declaredWidth, out int declaredHeight)
    || declaredWidth > MaxDecodeSide || declaredHeight > MaxDecodeSide)
{
    ...
    return false;
}
```

`JpegHeader.TryReadSize` (`JpegHeader.cs:16`) recorre los segmentos del JPEG hasta el primer marcador SOFn y lee ancho y alto. Si la estructura está truncada o malformada, devuelve `false`.

### Interop nativo: `Mat` sin copia y *pinning*

OpenCV es código nativo (C++). Para dibujar sobre un `Frame` sin copiar sus ~3,7 MB, se crea un `Mat` que **apunta** al `byte[]` gestionado. Problema: el GC puede **mover** un array; si OpenCV guarda la dirección y el array se mueve, lee basura. `GCHandle.Alloc(..., Pinned)` lo fija en su sitio mientras viva el `Mat`.

```csharp
// src/QualityVision.Infrastructure/Imaging/PinnedMat.cs:27-37, 46-56
_handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try
{
    Address = _handle.AddrOfPinnedObject();
    Mat = Mat.FromPixelData(rows, cols, type, Address, (long)cols * bytesPerPixel);
}
catch
{
    _handle.Free();
    throw;
}
...
public void Dispose()
{
    // Release the header first: it must never outlive the pin.
    Mat.Dispose();
    ...
        handle.Free();
}
```

Dos detalles: si el constructor falla, se libera el pin (si no, el array quedaría fijado para siempre) y en `Dispose` se libera el `Mat` **antes** que el pin. Además, todo `Mat` intermedio va dentro de un `using` (regla de `CLAUDE.md`): un `Mat` no liberado es una fuga nativa que el GC no ve.

## La software factory en M2

1. **Contract-first.** El orchestrator escribió `docs/contracts/M2-contract.md` (firmas de `Frame`, `IFrameSource`, `PhoneFrameSource`, `JpegFrameEncoder`, opciones y pipeline) y lanzó **tres agentes en paralelo**: backend-dev (Core + Web), vision-engineer (Infrastructure) y frontend-dev (`kamera.html` y dashboard). Pudieron trabajar a la vez porque cada uno programaba contra las firmas del contrato, no contra el código de los otros.
2. **QA.** El qa-engineer escribió la suite: **69 tests** (el contrato decía que `Frame`, el canal, el broadcaster, `PhoneFrameSource` y las opciones debían estar cubiertos).
3. **Reviewer.** Veredicto **APPROVE** (sin BLOCKER) con **3 MAJOR** y varios MINOR (`docs/reviews/M2-review.md`):
   - **Apagado colgado:** `/stream` no observaba `ApplicationStopping` → token enlazado (51 ms frente a ~30 s).
   - **Timeout al abrir una URL:** abrir un DroidCam inaccesible bloqueaba ~30 s y no se podía cancelar → timeouts de apertura (5 s) y lectura (3 s) en FFmpeg (`OpenCvFrameSource.cs:31-38`).
   - **DoS por bomba de descompresión** → comprobación SOF + `FrameUploadGate` + límite de cuerpo.
4. **Corrección + tests de regresión.** Los 3 MAJOR se arreglaron **antes** de cerrar el milestone, cada uno con tests (`JpegHeaderTests`, `FrameUploadGateTests`…). Resultado: **94 tests**.
5. **Pruebas reales con el iPhone** (lo que ningún test automático encuentra):
   - **Frames verticales:** llegaban de 1280×2276 y ~400 KB, mucho más de lo previsto → el límite pasó a ser el **lado más largo** (`CameraOptions.MaxSide`, `CameraOptions.cs:30`) en vez de un ancho fijo.
   - **Bloqueo de rotación del iPhone:** la imagen no giraba → botón **"Drehen ⟳"** en `kamera.html`.
   - **La "ü" no se ve:** las fuentes Hershey de OpenCV no soportan diacríticos; el primer intento de dibujar los puntos a mano quedó frágil (MINOR #6). Solución provisional: el texto **"PRUEFZONE"** (`JpegFrameEncoder.cs:79`). La solución definitiva es renderizar texto con **SkiaSharp en M3**, que además hará falta para etiquetas como "Löffel".

Lección: la revisión independiente encontró fallos de robustez; la prueba con el dispositivo real encontró fallos de uso. Hacen falta las dos.

Limitaciones honestas de M2: la zona se dibuja pero no se evalúa; el certificado es autofirmado; hay que reiniciar para cambiar de fuente; sin GPU, todo en CPU; el MJPEG consume más ancho de banda que un códec de vídeo.

## 3 preguntas de entrevista

**1. ¿Qué pasa si la inferencia es más lenta que la cámara?**
Nada malo: el canal entre captura e inferencia es acotado (capacidad 2) con `DropOldest`. Cuando se llena, descarta el frame más viejo y el callback `itemDropped` lo libera, así que la memoria y la latencia quedan acotadas. Se pierden frames, pero el que se procesa es siempre de los más recientes, que es lo que importa en inspección en vivo. Además `DetectionService` limita el ritmo a `Stream:MaxFps` y el endpoint de subida nunca espera a la inferencia.

**2. ¿Cómo evitas fugas de memoria nativa?**
Con propiedad explícita y `Dispose` en todos los caminos. Cada `Mat` está en un `using`; el `Frame` se libera una sola vez gracias a `Interlocked.Exchange`; y los frames que descarta o deja sin leer un canal se liberan en `itemDropped` o al parar el servicio. Cuando un `Mat` envuelve un array gestionado, `PinnedMat` fija el array con `GCHandle` y libera primero el `Mat` y luego el pin. Un `Mat` sin liberar no lo ve el GC, por eso la regla es estricta y la revisión la comprobó.

**3. ¿Por qué MJPEG y no WebRTC?**
Porque es mucho más simple y robusto para esta demo: un `<img src="/stream">` y una respuesta HTTP `multipart/x-mixed-replace`, sin JavaScript, sin señalización ni STUN/TURN. Codificamos el JPEG una vez y lo compartimos entre todos los clientes. La desventaja es el ancho de banda (no hay compresión entre frames), pero en una LAN con 15 FPS no es un problema. WebRTC tendría sentido en internet o con vídeo de alta resolución, y lo declaramos como limitación, no como algo que no conocemos.
