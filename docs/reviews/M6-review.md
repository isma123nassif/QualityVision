# M6 review: SQLite persistence, CSV export, Plan-B recording

**Scope:** uncommitted changes (`git diff HEAD` plus untracked files) checked against `docs/contracts/M6-contract.md` and `CLAUDE.md`.
**Reviewer:** code-reviewer (read-only). Time-boxed review: BLOCKER and MAJOR findings get detail, MINOR findings are short.
**Not run by the reviewer:** build, tests and format. They remain DoD steps 1–3 for the orchestrator. The QA test files (`tests/.../Web/EventPersistenceServiceTests.cs`, `InspectionCsvTests.cs`, `InMemoryDb.cs`) exist but were only skimmed.

## Verdict

**No BLOCKERs. 2 MAJORs** (CSV formula injection, and Plan-B recording speed). Both fixes are small. I recommend fixing them before the `feat(m6)` commit.

## Focus areas: results

| Focus | Result |
|---|---|
| Persistence never blocks the detection thread | **OK.** `InspectionLog.Add` raises `EventAdded` outside the lock, and each handler runs in its own try/catch (`InspectionLog.cs:147-166`). `OnEventAdded` only calls `TryWrite` on a bounded channel (1000, `DropOldest`, `EventPersistenceService.cs:162`). That call never waits and never fails, and all database I/O stays on the background service. |
| Shutdown flush | **OK.** Since .NET 8, hosted services stop sequentially in reverse registration order: Detection → Camera → Persistence → Initializer. The last events are therefore queued before persistence is cancelled. Cancellation inside the 1 s window falls through to the outer catch with the partial batch kept. The batch is merged with `TryRead` leftovers and written with `CancellationToken.None` (`:147-159`). Unsubscribing before draining is correct. |
| Startup ordering (seed before pipeline) | **OK.** `InspectionDatabaseInitializer` is a plain `IHostedService` registered before `EventPersistenceService`, `CameraService` and `DetectionService` (`Program.cs:85-90`). Hosted services start sequentially by default, so `EnsureCreated` and `Seed` finish before any frame is captured. `Seed` raises no `EventAdded`, so seeded events are not persisted again. Negative `Sequence` values avoid `@key` collisions. |

## MAJOR

### MAJOR-1: CSV formula injection (`InspectionCsv.Escape`, `src/QualityVision.Web/Endpoints/InspectionCsv.cs:35-41`)

`Escape` handles RFC-4180 quoting (`;`, `"`, CR/LF) correctly but does nothing about formula injection. If `Klasse` or `Bezeichnung` starts with `=`, `+`, `-`, `@` (or tab/CR), Excel evaluates it as a formula when the file is opened, e.g. `=HYPERLINK("http://…","Klick")`. The export target is explicitly German Excel (BOM and `;` exist only for that).

- **Source of the values:** `ClassName` comes from the YOLO-World vocabulary in config. `DisplayName` comes from the label mapping in config/rules. These files are operator-controlled. Under the LAN-only, no-auth design (ADR-001), anyone who can reach the config-editing surface could plant a payload that runs on the Excel workstation of whoever opens the export. Exploitability is low, but this is the textbook OWASP "CSV Injection" finding, and an interviewer may ask about it while looking at an export button.
- **Fix (about 3 lines, pure function, easy to test):** in `Escape`, if `value.Length > 0 && "=+-@\t\r".Contains(value[0])`, prefix the value with `'`, then apply the existing quoting rule. Add `InspectionCsvTests` cases for `=1+1`, `+x`, `-x`, `@x` and for a value that needs both the prefix and quoting (e.g. `=a;b`).
- Timestamp, verdict label and confidence are generated by the app and are safe. A negative confidence is impossible.

### MAJOR-2: the recorded video plays too fast (`FrameRecorder.TryWrite`, `src/QualityVision.Infrastructure/Camera/FrameRecorder.cs:60-71`)

The file declares 15 fps, but the recorder only *skips* frames that arrive within 66.7 ms of the last written one. It never writes a frame twice to fill a gap. The content rate therefore depends on the source rate:

- With the default `Camera:MaxFps = 20` (50 ms spacing), frames are written at t = 0, 100, 200 ms… The 50 ms gap is under 66.7 ms and is skipped, so only **10 frames/s** are written into a 15 fps file.
- Any source slower than 15 fps (phone, a busy DroidCam) writes every frame, so it also under-fills.

`OpenCvFrameSource` paces file playback by the container FPS (`GetFileFps`). The Plan-B video therefore plays at **1.5× speed** with the default settings, and a 120 s recording lasts about 80 s. Objects visibly move too fast in front of the interviewers. This breaks the contract's "fixed 15 fps" in practice, even though the file header says 15.

- **Fix:** write by slot instead of by interval. Compute `long due = (long)((frame.CapturedAt - _firstAt) / FrameInterval) + 1;`, then write the current frame `due - _frames` times (cap at a few repeats, e.g. 5, to survive stalls). Do the BGRA→BGR conversion and resize once and call `_writer.Write` repeatedly. A 20 fps source then gives exactly 15 fps of real time, and a 10 fps source gets each frame duplicated. Neither `RecordMaxSeconds` nor ownership is affected.
- **Test (the contract asks for a FrameRecorder test, which does not exist yet):** feed N frames spaced 50 ms apart over 2 s (`CapturedAt` from a `FakeTimeProvider`). Read the file back with `VideoCapture` and expect about 30 frames, not about 20.

## MINOR

1. **Two databases, invisible in the published layout.** The demo uses `artifacts/demo/data/qualityvision.db` and `dotnet run` uses `src/QualityVision.Web/data/…`. `rm -rf artifacts` deletes the demo history. Print the DB path in `run-demo.sh`, next to the `rules.json` line.
2. **`Camera:VideoFile = samples/demo.mp4` (relative)** does not resolve from `artifacts/demo` unless `--video` is used. That is fine for M6, but the automatic camera→video fallback planned in CLAUDE.md would hit this. Note it in `samples/README.md` or resolve the path against the repo in the script.
3. **No WAL.** `await foreach` in the CSV export keeps a read cursor open while streaming to the client. In rollback-journal mode this blocks the persistence commit until `busy_timeout` (30 s) expires, and the batch is then lost (logged). Exports are tiny today. Run `PRAGMA journal_mode=WAL;` once in the initializer (`.gitignore` already covers `*-wal`), or use `ToListAsync` for the export.
4. **Web references `Microsoft.Data.Sqlite` directly** (`Program.cs:49-55`). Path resolution and directory creation belong in `AddInspectionPersistence(connectionString, contentRootPath)` in Infrastructure. The current block also turns `Data Source=:memory:` into a file called `:memory:` under the content root.
5. **No midnight rollover.** `Counts` is documented as "for the current day" (`InspectionLog.cs:31`), but if the app runs past midnight it keeps yesterday's totals until restart, while the seed and the CSV default are per-day. Fix the doc comment, or note it as a known limitation.
6. **If initialization fails, persistence keeps trying** and logs `no such table` about once per second for every batch. It is acceptable ("log and continue") but noisy. Consider a flag that turns persistence off once initialization fails.
7. **DropOldest drops are silent.** Consider a `LogWarning` (rate-limited) when the channel is full; `TryWrite` itself can't tell, so compare `Reader.Count` against the capacity.
8. **`DatabaseHealthCheck`**: for SQLite, `CanConnectAsync` creates the file when it is missing, so the check is almost always Healthy. That is fine for a demo and allowed by the contract (`AddDbContextCheck` is not in CPM). Name the limitation in the ADR or learning notes.
9. **CSV endpoint:** `WriteAsync(string)` calls ignore `cancellationToken`. Pass it (`WriteAsync(ReadOnlyMemory<char>, ct)`), or rely on `RequestAborted` exceptions. Only `yyyy-MM-dd` is accepted, not full ISO date-times; that is fine, but document it. A database failure after the first flush gives a truncated 200 response, which is acceptable.
10. **`CameraService.CreateRecorder`** runs `Path.GetFullPath` outside any try/catch. A pathological `RecordTo` (e.g. containing NUL) would fault `CameraService` and stop the host. Wrap it so that recording failures "never break capture".
11. **Recording while `--video` is active** with `RecordTo` pointing at the same `samples/demo.mp4` would overwrite the file being played. Edge case: one sentence in `samples/README.md`.
12. **Tests:** there is no `FrameRecorder` read-back test yet (contract item 3); see MAJOR-2. The seed test should cover the local-day boundary: an event at 23:59 local yesterday must not be counted.

## Positives

- `InspectionLog.Add` already isolated subscribers, so persistence plugs in without touching the detection path.
- Hosted-service order is explicit and explained in a comment, and the trade-off of no migrations is documented where `EnsureCreated` is called.
- `LocalDay` uses half-open ranges with `TimeProvider` and no `DateTime.Now`, which follows CLAUDE.md.
- The recorder's ownership comment and the "error logged once, then disabled" rule match the contract exactly.
- In `run-demo.sh --video`, the absolute path, the existence check and the quoting are correct, and the script still uses `exec`, so SIGTERM reaches the app.
